# Plan: `temporalio.local_server.LocalServer`

## Problem

The SDK can download and run a local Temporal dev server, but this capability is buried inside
`temporalio.testing.WorkflowEnvironment.start_local()` — a test-only API that conflates server
lifecycle with client creation and test interceptors. Users who simply want to run a local server
from Python (e.g. for getting-started workflows, local development, or scripts) have no clean way
to do so.

## Requirements

1. New public class `LocalServer` in `temporalio.local_server`.
2. Two lifecycle patterns:
   - Async context manager: `async with LocalServer(...) as server:`
   - Explicit: `server = LocalServer(...); await server.start(); ... await server.shutdown()`
3. Expose `target` (the gRPC address) so users can connect a `Client` to it.
4. Share the underlying `temporalio.bridge.testing.EphemeralServer` / `DevServerConfig` machinery.
5. Refactor `WorkflowEnvironment.start_local()` to use `LocalServer` internally, avoiding code
   duplication.

## Design

### `temporalio.local_server` module

A single new file `temporalio/local_server.py` containing `LocalServer`.

```python
class LocalServer:
    """A local Temporal dev server.

    Can be used as an async context manager or via explicit start()/shutdown().
    """

    def __init__(self, *, namespace="default", ip="127.0.0.1", port=None, ...): ...

    async def start(self) -> None: ...
    async def shutdown(self) -> None: ...
    async def __aenter__(self) -> Self: ...
    async def __aexit__(self, ...) -> None: ...

    @property
    def target(self) -> str: ...
```

**Constructor** accepts server configuration but does NOT start the server. This is the normal
pattern for objects with explicit `start()`.

**`start()`** downloads the CLI binary (if needed) and starts the dev server process. Returns
`None` — side-effectful methods should be void. Raises if already started.

**`shutdown()`** stops the server process. Idempotent — safe to call before `start()`, after
`shutdown()`, or multiple times.

**`target`** returns the gRPC frontend address (e.g. `"127.0.0.1:7233"`). Raises if not started.

### Parameters

Mirror the dev-server-specific parameters from `WorkflowEnvironment.start_local()`:

| Parameter | Type | Default | Notes |
|-----------|------|---------|-------|
| `namespace` | `str` | `"default"` | |
| `ip` | `str` | `"127.0.0.1"` | |
| `port` | `int \| None` | `None` | OS-assigned if None |
| `database_filename` | `str \| None` | `None` | SQLite path; None = in-memory |
| `ui` | `bool` | `False` | |
| `ui_port` | `int \| None` | `None` | |
| `log_format` | `str` | `"pretty"` | |
| `log_level` | `str \| None` | `"warn"` | None → derive from Python logger |
| `download_dest_dir` | `str \| None` | `None` | |
| `download_version` | `str` | `"default"` | |
| `download_ttl` | `timedelta \| None` | `None` | |
| `existing_path` | `str \| None` | `None` | Skip download |
| `extra_args` | `Sequence[str]` | `[]` | |
| `search_attributes` | `Sequence[SearchAttributeKey]` | `()` | |
| `runtime` | `Runtime \| None` | `None` | |

Note: we drop the `dev_server_` prefix since there is no ambiguity in this context.

### Refactoring `WorkflowEnvironment.start_local()`

After `LocalServer` exists, `start_local()` should construct and start a `LocalServer`, then
connect a client to `server.target`. The `_EphemeralServerWorkflowEnvironment` will hold a
`LocalServer` instead of directly holding a `bridge.testing.EphemeralServer`. This keeps the
server lifecycle logic in one place.

We'll need a minor internal hook: `_EphemeralServerWorkflowEnvironment` currently accesses
`server.has_test_service` — but `LocalServer` wraps a dev server which never has the test service,
so we can hardcode `False` in that path (or expose the underlying `EphemeralServer` via a private
attribute).

### Approach

The simplest approach: `LocalServer` owns the bridge-level `EphemeralServer` and exposes a clean
public API. `WorkflowEnvironment.start_local()` constructs a `LocalServer`, starts it, and wraps
the result. We extract the shared config-building logic (log level derivation, search attribute
arg construction) into a private helper in `local_server.py`.

## Components to create/modify

1. **Create** `temporalio/local_server.py` — the `LocalServer` class.
2. **Modify** `temporalio/testing/_workflow.py` — refactor `start_local()` to use `LocalServer`.
3. **Modify** `temporalio/testing/__init__.py` — no changes needed (doesn't export server).
4. **Create** `tests/test_local_server.py` — tests for `LocalServer`.

## Implementation steps

1. Create `temporalio/local_server.py` with `LocalServer`.
2. Write tests in `tests/test_local_server.py`:
   - Test context manager lifecycle (start, connect client, describe namespace to verify server
     is operational, shutdown).
   - Test explicit start/shutdown lifecycle (same light verification).
   - Test `target` raises before `start()`.
   - Test double-start raises.
   - Test shutdown idempotency (including before `start()`).
3. Refactor `WorkflowEnvironment.start_local()` to delegate to `LocalServer`.
4. Run existing tests to confirm no regressions.

## Verification

Run:
```bash
# New tests
uv run pytest tests/test_local_server.py -v

# Existing tests that exercise start_local / WorkflowEnvironment
uv run pytest tests/ -k "test_" --timeout 120 -x
```

The new tests must pass with the implementation and fail without it (i.e. reverting the
`local_server.py` file should cause them to fail).

## Resolved decisions

- **No sync API** — async-only, consistent with the rest of the SDK.
- **No convenience `Client` factory** — keep focused on server lifecycle; users call
  `Client.connect(server.target)`.
