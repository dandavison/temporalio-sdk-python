# Plan: `async with Server(...)` context manager

## Background

### Current state

The Python SDK has a `WorkflowEnvironment.start_local()` class method in `temporalio.testing` that:
1. Downloads the Temporal CLI dev server binary (via Rust bridge in `temporalio.bridge.testing`)
2. Starts the server process
3. Connects a `Client` to it
4. Wraps everything in a `WorkflowEnvironment` that adds test-specific interceptors (assertion
   error conversion) and exposes test helpers (`sleep`, `get_current_time`, time-skipping)

The download/start machinery lives in `temporalio.bridge.testing.EphemeralServer` (Rust bridge)
with `DevServerConfig` and `TestServerConfig` dataclasses. Tests use
`WorkflowEnvironment.start_local()` via conftest.py fixtures.

### What other SDKs do

The **Go SDK** has a public `DevServer` type in its `testsuite` package with `StartDevServer()`,
`Stop()`, `Client()`, and `FrontendHostPort()` methods. It's the most relevant prior art: a
standalone server handle that owns the process and a connected client, without test-framework
concerns mixed in.

The .NET and TypeScript SDKs keep the server concept internal to the test environment.

### Goal

Create a `Server` class that:
- Can be used as `async with Server(...)` (async context manager), mirroring `async with Worker(...)`
- Downloads and starts a local Temporal dev server
- Shares the existing download machinery with the test infrastructure
- Is a first-class SDK concept (not coupled to the test framework)
- Allows `WorkflowEnvironment.start_local()` to be refactored to use it (optional follow-up)

## Design

### Where to put `Server`

**Not in `temporalio.testing`**: The `Server` is a general-purpose utility for anyone wanting a
local Temporal server - demos, scripts, development, integration tests. It should be a peer of
`Worker`, not a testing-only concept.

**Proposed location**: `temporalio.server` module (new file `temporalio/server.py` or package
`temporalio/server/`). A single file is sufficient initially.

**Import**: `from temporalio.server import Server` (and re-export from `temporalio` top-level if
that's the pattern used for `Worker` - need to check).

### API design

```python
class Server:
    """A locally-running Temporal dev server.

    This downloads (if necessary) and runs a Temporal CLI dev server. It is
    an async context manager, so it can be used with ``async with``::

        async with Server() as server:
            client = await Client.connect(server.target)
            # ... use client ...

    The dev server binary is downloaded on first use and cached.
    """

    def __init__(
        self,
        *,
        # Server config
        namespace: str = "default",
        ip: str = "127.0.0.1",
        port: int | None = None,
        database_filename: str | None = None,
        ui: bool = False,
        ui_port: int | None = None,
        log_format: str = "pretty",
        log_level: str = "warn",
        extra_args: Sequence[str] = [],
        # Download config
        existing_path: str | None = None,
        download_version: str = "default",
        download_dest_dir: str | None = None,
        download_ttl: timedelta | None = None,
        # Runtime
        runtime: temporalio.runtime.Runtime | None = None,
    ) -> None:
        ...

    async def start(self) -> None:
        """Start the server. Called automatically by ``async with``."""
        ...

    async def shutdown(self) -> None:
        """Shutdown the server. Called automatically by ``async with``."""
        ...

    async def __aenter__(self) -> Server:
        await self.start()
        return self

    async def __aexit__(self, *args) -> None:
        await self.shutdown()

    @property
    def target(self) -> str:
        """The host:port of the running server's frontend gRPC endpoint."""
        ...
```

### Key design decisions

1. **Constructor stores config; `start()` does the work.** This mirrors the Go SDK's separation of
   config from starting, and allows the `async with` pattern to work naturally. The constructor is
   cheap (no I/O); all I/O happens in `start()` / `__aenter__`.

2. **No built-in `client` property.** Unlike the Go SDK's `DevServer.Client()`, we do not create a
   client automatically. Rationale: the Python SDK's `Client.connect()` has many parameters (data
   converter, interceptors, etc.) that the user should control. Providing a `target` property is
   sufficient and avoids the need to mirror `Client.connect()`'s parameters. This also avoids the
   `WorkflowEnvironment.start_local()` pattern of having a large parameter list that's half server
   config and half client config. The user writes:
   ```python
   async with Server() as server:
       client = await Client.connect(server.target)
   ```

3. **Parameters match `WorkflowEnvironment.start_local()` dev-server params but without the
   `dev_server_` prefix.** Since this class is specifically a dev server, the prefix is redundant.

4. **Reuses `temporalio.bridge.testing.EphemeralServer` and `DevServerConfig` internally.** The
   bridge module is marked "unstable" but that's fine for internal use.

5. **The `DEV_SERVER_DOWNLOAD_VERSION` constant currently in `tests/__init__.py` is test-specific**
   (it pins a particular version for CI reproducibility). The `Server` class uses `"default"` which
   maps to the SDK-default version baked into the Rust core. Tests that want a pinned version pass
   `download_version=DEV_SERVER_DOWNLOAD_VERSION` explicitly.

### Refactoring `WorkflowEnvironment.start_local()` (follow-up)

Once `Server` exists, `WorkflowEnvironment.start_local()` can be refactored to use it internally.
This is a separate commit/PR to keep the initial change focused. The refactoring would:
- Create a `Server` internally, call `start()`
- Connect a client to `server.target`
- Wrap in `_EphemeralServerWorkflowEnvironment`
- Ensure `shutdown()` calls both `server.shutdown()` and any client cleanup

This is optional and should be discussed separately.

## Implementation plan

### Step 1: Create `temporalio/server.py`

New file containing the `Server` class. Implementation:
- Store all config in `__init__`
- In `start()`: build a `DevServerConfig`, call
  `temporalio.bridge.testing.EphemeralServer.start_dev_server()`, store the result
- In `shutdown()`: call `self._server.shutdown()`
- `target` property delegates to `self._server.target`
- Raise `RuntimeError` if `target` or `shutdown` called before `start`

### Step 2: Export from `temporalio/__init__.py` (if appropriate)

Check whether the SDK re-exports `Worker` from `temporalio` top-level. If so, also re-export
`Server`. If not (i.e. users do `from temporalio.worker import Worker`), then users would do
`from temporalio.server import Server`.

### Step 3: Write tests

Add a test that:
1. Starts a `Server` via `async with`
2. Connects a client to `server.target`
3. Runs a simple workflow
4. Verifies it completes successfully

This can go in a new `tests/test_server.py` or be added to an existing test file.

### Step 4: Update `WorkflowEnvironment.start_local()` to use `Server` (if desired)

Refactor the internals to delegate to `Server`. All existing tests should continue to pass
unchanged.

## Open questions for review

1. **Module location**: `temporalio/server.py` vs `temporalio/server/__init__.py` (package)? A
   single file is simpler now; we can always convert to a package later if needed.

2. **Should `Server` accept `search_attributes`?** `WorkflowEnvironment.start_local()` has this
   parameter and converts them to `--search-attribute` CLI args. It's a convenience that avoids the
   user having to know the CLI flag format. Leaning yes.

3. **Should we include `http_port`?** The test conftest passes `--http-port` via `extra_args`. Could
   be a named parameter for discoverability, or left to `extra_args`. Leaning: leave to
   `extra_args` for now.

4. **Name**: `Server` is clean and matches the `Worker` pattern. Alternatives: `DevServer` (more
   explicit about what it is, matches Go SDK), `LocalServer`. The Go SDK uses `DevServer`. Since
   this is specifically the Temporal CLI dev server and future versions might support other server
   types, `DevServer` may be more precise. But `Server` is simpler and the docstring makes it clear.
   **Recommendation: start with `DevServer` for precision, matching Go SDK precedent.** Can always
   add a `Server` alias later.
