# Plan 2: `async with DevServer(...)` context manager

This is an iteration on plan 1, incorporating research into the codebase and prior art.

## Naming: `DevServer`, not `Server`

The Go SDK uses `DevServer` in its `testsuite` package. The Python SDK's underlying bridge already
uses the term "dev server" (`DevServerConfig`, `start_dev_server`). The existing test code uses the
term throughout. "Server" is too generic — this is specifically the Temporal CLI dev server, and if
we ever support other server types (e.g. a real server, a mock, or the time-skipping test server),
we'd want distinct names. `DevServer` is more honest and matches precedent.

## Module location: `temporalio/contrib/devserver.py`

The SDK doesn't re-export anything at the top level (users do `from temporalio.worker import Worker`,
`from temporalio.testing import WorkflowEnvironment`, etc.).

Considered locations:

- **`temporalio/server.py`** (plan 1): Overly generic. This is specifically the CLI dev server, not
  a general server abstraction.
- **`temporalio/testing/`**: That's where the machinery already lives, but the DevServer is useful
  beyond testing (demos, scripts, local dev). Putting it in `testing` would imply it's test-only.
- **`temporalio/contrib/devserver.py`**: Signals that this is a convenience utility built on top of
  the core SDK, not a core primitive. It avoids over-committing on the API surface: we can graduate
  it later if it proves stable enough. This is a common pattern in Python libraries (Django contrib,
  etc.).
- **`temporalio/devserver.py`**: Direct and simple. Makes it a peer of `worker`, `client`,
  `testing`. Slightly over-elevates what is essentially a convenience wrapper around the bridge.

**Decision: `temporalio/contrib/devserver.py`**. New `temporalio/contrib/` package (with
`__init__.py`). Import: `from temporalio.contrib.devserver import DevServer`.

**Alternative worth discussing**: `temporalio/devserver.py` — simpler, but may imply more stability
commitment than warranted for a first iteration.

## API design

```python
class DevServer:
    """A locally-running Temporal CLI dev server.

    Downloads (if necessary) and runs a Temporal CLI dev server process. The
    binary is cached after the first download.

    Can be used as an async context manager::

        from temporalio.contrib.devserver import DevServer

        async with DevServer() as server:
            client = await Client.connect(server.target)
            async with Worker(client, task_queue="my-tq", workflows=[...]):
                ...

    Or managed explicitly::

        server = DevServer()
        await server.start()
        try:
            client = await Client.connect(server.target)
            ...
        finally:
            await server.shutdown()
    """

    def __init__(
        self,
        *,
        # Server config
        namespace: str = "default",
        ip: str = "127.0.0.1",
        port: int | None = None,
        database_filename: str | None = None,
        ui: bool = False,
        ui_port: int | None = None,
        log_format: str = "pretty",
        log_level: str = "warn",
        search_attributes: Sequence[temporalio.common.SearchAttributeKey] = (),
        extra_args: Sequence[str] = [],
        # Download config
        existing_path: str | None = None,
        download_version: str = "default",
        download_dest_dir: str | None = None,
        download_ttl: timedelta | None = None,
        # Runtime
        runtime: temporalio.runtime.Runtime | None = None,
    ) -> None: ...

    async def start(self) -> None: ...
    async def shutdown(self) -> None: ...

    async def __aenter__(self) -> DevServer: ...
    async def __aexit__(self, *args: Any) -> None: ...

    @property
    def target(self) -> str:
        """The host:port of the frontend gRPC endpoint."""
        ...
```

### Key decisions

1. **Constructor stores config; `start()` does I/O.** Same pattern as the Go SDK's
   `StartDevServer` (config struct + start function), adapted to Python's `async with` idiom where
   the constructor is the config and `__aenter__` does the start.

2. **No `client` property.** The Go SDK returns a pre-built client, but the Python SDK's
   `Client.connect()` has many parameters (data converter, interceptors, plugins, etc.). Rather than
   duplicating that parameter surface, we expose `target` and let the user connect however they want.
   This is the same conclusion as plan 1 and it's the right one: it keeps DevServer focused on
   exactly one thing (running the server process).

3. **`search_attributes` parameter.** Included because `WorkflowEnvironment.start_local()` has it
   and it's a common need. The implementation converts `SearchAttributeKey` to `--search-attribute`
   CLI args, same as the existing code.

4. **Parameters match `WorkflowEnvironment.start_local()` dev-server params without the
   `dev_server_` prefix.** The prefix is redundant when the class is already called DevServer.

5. **`log_level` defaults to `"warn"`, not `None`.** Unlike `WorkflowEnvironment.start_local()`
   which has a `None` option that maps Python logger levels to dev server levels, the DevServer is
   not a testing class and shouldn't have testing-specific convenience logic. If users want to sync
   with Python logging, they can do it themselves. Keeps the class simple.

## Internal implementation

The `start()` method:

```python
async def start(self) -> None:
    if self._server is not None:
        raise RuntimeError("Already started")
    runtime = self._runtime or temporalio.runtime.Runtime.default()
    extra_args = list(self._extra_args)
    for attr in self._search_attributes:
        extra_args = ["--search-attribute", f"{attr.name}={attr._metadata_type}"] + extra_args
    download_ttl_ms = (
        int(self._download_ttl.total_seconds() * 1000)
        if self._download_ttl is not None
        else None
    )
    self._server = await temporalio.bridge.testing.EphemeralServer.start_dev_server(
        runtime._core_runtime,
        temporalio.bridge.testing.DevServerConfig(
            existing_path=self._existing_path,
            sdk_name="sdk-python",
            sdk_version=temporalio.service.__version__,
            download_version=self._download_version,
            download_dest_dir=self._download_dest_dir,
            namespace=self._namespace,
            ip=self._ip,
            port=self._port,
            database_filename=self._database_filename,
            ui=self._ui,
            ui_port=self._ui_port,
            log_format=self._log_format,
            log_level=self._log_level,
            extra_args=extra_args,
            download_ttl_ms=download_ttl_ms,
        ),
    )
```

This is essentially the same code currently in `WorkflowEnvironment.start_local()` lines 160-205,
minus the client connection and minus the Python-log-level mapping.

## Refactoring `WorkflowEnvironment.start_local()`

Once DevServer exists, `start_local()` can be refactored to use it internally. This is a separate
commit to keep the initial change focused. The refactoring would:

1. Create a `DevServer` with the appropriate config
2. Call `await server.start()`
3. Connect a client to `server.target`
4. Wrap in `_EphemeralServerWorkflowEnvironment`
5. On failure, call `server.shutdown()` (same error handling as today)

The `log_level=None` -> Python-logger-level mapping is a `start_local()` concern and stays there;
it would compute the string before passing it to DevServer.

This refactoring is optional for the initial PR. It's clean to do but it's a separate question
from "does DevServer exist".

## Open questions

1. **`contrib` vs `devserver` at top level?** The `contrib` package adds a level of indirection.
   `from temporalio.devserver import DevServer` is more direct. Counter-argument: `contrib` signals
   "not core, may evolve". I lean `contrib` but this is a taste question.

2. **Should the refactoring of `start_local()` be in the same PR?** It's clean and removes
   duplication, but it changes existing code paths. Leaning: separate PR.

3. **`download_version` default.** Currently `"default"` maps to whatever the Rust bridge considers
   the default. Tests pin a specific version via `DEV_SERVER_DOWNLOAD_VERSION`. The DevServer class
   uses `"default"`, which is correct — it should track the SDK's known-good version, not the test
   suite's pinned version.
